# Scope Guard

Check whether proposed or actual changes stayed inside the agreed scope. This skill is strict and read-only.

Use it before implementation, when drift is suspected, or before git review and commit. It does not fix drift.

## Required outcomes

- Identify the scope source.
- Identify the change baseline being reviewed.
- Classify changes as `IN SCOPE`, `INCIDENTAL`, `SUSPICIOUS`, or `BLOCKING DRIFT`.
- Provide file and line references where available.
- End with exactly one review outcome.

## Core rules

- Never edit files.
- Never stage, commit, push, reset, stash, amend, or otherwise mutate git state.
- Never mutate external systems.
- Prefer evidence over assumption.
- Judge changes against the approved request, strategy, task boundary, or explicit scope.
- Flag scope drift even when the change seems useful.
- Do not silently repair drift.
- If scope context is partial, report confidence and the missing context.

## Allowed

- Read source, tests, docs, plans, strategies, and diffs.
- Inspect working tree, staged, branch, or PR diffs with read-only commands.
- Run clearly non-mutating inspection commands.
- Produce findings and required follow-up actions.

## Forbidden

- Do not edit, move, delete, format, generate, or rewrite files.
- Do not stage, commit, split, stash, reset, push, or amend.
- Do not run fixers, formatters, generators, migrations, package installers, or snapshot updates.
- Do not approve unclear scope as in-scope.
- Do not recommend silently keeping drift because it seems useful.

## Review inputs

Use the narrowest available scope source:

- user-stated scope
- approved strategy or task boundary
- current task boundary
- explicit file list or module boundary

Use the narrowest available change baseline:

- proposed file list or patch
- working tree diff
- staged diff
- branch diff
- PR diff
- current task changes

If either scope source or change baseline is missing, report `NO SCOPE BASELINE`.

## Classifications

- `BLOCKING DRIFT`: clearly out-of-scope work that should block progress until removed, split, or explicitly approved.
- `SUSPICIOUS`: potentially out-of-scope work that needs clarification before proceeding.
- `INCIDENTAL`: extra change that is acceptable because it is required, localized, mechanical, or generated by an approved command.
- `IN SCOPE`: directly implements or verifies the approved scope.

## Flag when present

- unrelated file changes
- opportunistic refactors
- unapproved dependency changes
- formatting-only churn mixed into semantic work
- architecture changes not present in the approved scope or strategy
- tests rewritten to match implementation rather than protect behaviour
- broad edits that exceed the stated request
- generated or snapshot changes without an approved reason
- new public contracts not called for by the scope

## Workflow

1. Identify the scope source and change baseline.
2. Inspect the relevant proposed or actual changes.
3. Classify changed areas with evidence and file/line references where available.
4. Distinguish unclear scope from confirmed out-of-scope change.
5. Choose exactly one required follow-up action:
   - proceed
   - ask for scope approval
   - split unrelated work
   - remove drift manually
   - update the strategy before continuing
6. Report findings without editing.

## Readiness gate

Scope Guard Findings are useful only when:

- the scope source is explicit enough to judge against
- the change baseline is inspectable
- findings cite concrete files, hunks, or proposed changes where possible
- confidence is stated when context is incomplete

If the scope source or baseline is absent, do not infer. Return `NO SCOPE BASELINE`.

## Stop immediately when

- a needed inspection command may mutate state
- scope cannot be established
- the change baseline cannot be inspected
- the user asks the skill to fix drift directly
- an external system mutation would be required

## Output format

Lead with out-of-scope or suspicious findings when any exist. Use this structure:

```md
# Scope Guard Findings

## Scope Source
- Source:
- Confidence:

## Change Baseline
- Baseline reviewed:

## Findings
- [BLOCKING DRIFT | SUSPICIOUS | INCIDENTAL | IN SCOPE] file:line
  Scope judgement:
  Evidence:
  Required action:

## In-Scope Changes
## Acceptable Incidental Changes
## Out-of-Scope or Suspicious Changes
## Required Follow-Up Action
- proceed | ask for scope approval | split unrelated work | remove drift manually | update strategy

## Confidence

## Review Outcome
- PASS | PASS WITH INCIDENTALS | BLOCKED BY DRIFT | NO SCOPE BASELINE
```

End with exactly one review outcome:

- `PASS`: reviewed changes are in scope.
- `PASS WITH INCIDENTALS`: incidental changes are acceptable and explained.
- `BLOCKED BY DRIFT`: blocking or unresolved suspicious changes remain.
- `NO SCOPE BASELINE`: scope source or change baseline is missing.
